- Add `parseLocalDateTime('YYYY-MM-DDTHH:mm')` to `dates.js`, built with `new Date(y, m-1, d, hh, mm)`. Use it in the clock, and use it anywhere else a local timestamp string becomes a `Date`.

## 2. `domain/meeting.js`
- **`meetingStatus(meeting, now)`** returns `'cancelled'` when `meeting.cancelled` is true. Otherwise, by local date and time:
  - before `start` → `'upcoming'`
  - from `start` until before `end` → `'ongoing'`
  - at or after `end` → `'done'`
  - The end is exclusive, so 09:40 for a 09:00–09:40 meeting is `'done'`.
  - Past-dated meetings are allowed and simply show as `done` (review P0-3).
- **`validateMeeting(input, refs)`**
  - `refs` is `{ roomById, personById }` from `data/reference.js`. It is injected, so tests can pass fakes.
  - Returns an **array** of `{ field, code }`. It is empty when valid. Codes are exactly the `meeting.*` codes already in `error.*`.
  - Field order matches the form: title, date, start/end, room, attendees.
  - Checks:
    - title is required (trimmed, max 40 chars → `meeting.title.tooLong`)
    - date is a valid date
    - start and end are valid times, and end > start
    - roomId exists
    - `attendeeIds` is non-empty, every id exists, with no duplicates
    - agenda is optional, max 500 → `meeting.agenda.tooLong`
  - Add any new codes to **both** locale files under `error.*`.
- **`createMeeting(input, { id, organizerId, now })`** returns a new record with:
  - every field from DESIGN.md 小程序字段
  - `cancelled: false`
  - `createdAt` from `now`, as a local `YYYY-MM-DDTHH:mm` string
  - No `status` field.
  - It does not validate; the caller validates first.
  - `title` and `agenda` are stored trimmed, as plain strings. User text is never translated.
- **`cancelMeeting(meeting, { role, personId, now })`** returns:
  - `{ ok: true, meeting: newRecord }` with `cancelled: true` and a `cancelledAt` timestamp, or
  - `{ ok: false, code }`, where code is `meeting.cancel.notAllowed`, `meeting.cancel.alreadyStarted`, or `meeting.cancel.alreadyCancelled` (a new code; add it to both locales).
  - Never mutate the input.
- **`findConflicts(candidate, meetings)`** is a non-blocking warning source (review P1-4). It returns `[{ type: 'room' | 'attendee', meetingId, personId? }]`:
  - same date with overlapping `[start, end)`
  - the other meeting is not cancelled
  - it is not the candidate itself (same id)
  - a room conflict needs the same `roomId`, and the room is not `online` (use `refs.roomById(id).online`; take `refs` as a third param)
  - an attendee conflict produces one entry per overlapping person
- **`sortMeetings(meetings)`** sorts by date, then start, then id (review P1-6: by date and time, not by status). It returns a new array.
- **`filterMeetings(meetings, filter, now)`**: `filter` is `all | upcoming | ongoing | done | cancelled`, using the derived status.

## 3. `domain/schedule.js` (review P0-5)
- `scheduleItems(date, sources, now)` builds the day's list from item sources.
  - `sources` is an array of adapters `{ kind, items, toScheduleItem(item, now) }`.
  - It returns items for `date`, sorted by `start`, then `kind` (meeting before vehicle), then id.
  - Each item has the shape `{ kind: 'meeting' | 'vehicle', id, date, start, end|null, status, ref }`, where `ref` is the original record.
- Export two ready adapters:
  - `meetingSource(meetings)`: status via `meetingStatus`. **Cancelled meetings are excluded** from the schedule's active view.
  - `vehicleSource(vehicles)`: `start = time`, `end = null`. **Excludes `rejected`.** Read-only in the MVP.
- `datesWithItems(sources, dates, now)` returns a `Set` (or an object map) of dates that have at least one item. The week strip uses it for its dots.

## 4. `domain/vehicle.js`: transition table only, no UI actions yet (review P1-5, last bullet)
- `TRANSITIONS = { pending: { dispatch: 'assigned', reject: 'rejected', withdraw: 'withdrawn' }, assigned: { complete: 'done', reassign: 'assigned', cancelDispatch: 'pending' }, done: {}, rejected: {}, withdrawn: {} }`
  - Add `withdrawn` to `status.vehicle` in both locales: zh `已撤回`, en `Withdrawn`.
- `ACTION_CAP = { dispatch: 'vehicle.dispatch', reject: 'vehicle.reject', complete: 'vehicle.complete', reassign: 'vehicle.dispatch', cancelDispatch: 'vehicle.dispatch', withdraw: 'vehicle.request' }`
- `availableActions(vehicle, role, personId)` lists the actions allowed by both the table and the capability. `withdraw` is only for the applicant.
- `transition(vehicle, action, payload, { role, personId, now })` returns `{ ok, vehicle | code }`.
  - On a stale state it returns `vehicle.alreadyHandled`.
  - On a missing capability it returns `permission.denied`.
  - Dispatch needs `carId` (`vehicle.car.required`). Reject needs a non-empty reason (`vehicle.reject.reasonRequired`).
  - It sets `dispatchedAt` / `dispatchedBy` / `completedAt` / `driverId`; the default driver is the current person if they are in DRIVERS.
  - This is groundwork for Sprint 2. Keep it small and fully tested.
