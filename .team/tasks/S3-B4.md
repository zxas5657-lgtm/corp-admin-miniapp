## 0. Rules that hold everywhere
- **Domain logic stays in `miniprogram/domain/`.** Handlers load the caller, read documents, convert them, call the same domain functions `local.js` uses, convert back, and write. If a rule the server needs is not in the domain yet, put it there (not in the handler) with a test, and have `local.js` use it too.
- **Documents ↔ domain:** add `cloudfunctions/_lib/docs.js`.
  - `toDomain(doc)`: `_id` → `id`; Date → ISO string, deep, including `leaders[]`.
  - `toDoc(record)`: drop `id`; convert the instant fields (`startAt`, `endAt`, `departAt`, `createdAt`, `updatedAt`, `cancelledAt`, `confirmedAt`, `changedAt`, `seenAt`, `handledAt`, `dispatchedAt`, `completedAt`, `arrivedAt`, `plateClearAfter`) from ISO to Date. Deep, so the `leaders[]` timestamps are converted too.
  - Never put `_id` in `set`/`update` data.
- **Paging:** `fetchAll(query, { max = 1000 })` in `_lib/` loops `skip`/`limit(100)`. Use it for every list read.
- **Visibility is filtered on the server.** Read candidates with a coarse DB query (a time range, plus `kind` where it helps), then filter with `domain/visibility.js` using `loadSupports(db)`. A `get` or write on an item the caller cannot see returns `item.notVisible` (vehicles: `permission.denied`, as in `local.js`). Never return an invisible record or reveal that it exists.
- **Concurrency:** every write by id runs in `db.runTransaction`. It re-reads the doc **by id**, compares `expectedRev` (when given) with `doc.rev` (`item.alreadyChanged` / `vehicle.alreadyHandled`), then writes `rev + 1`. Remember there is no `where` inside a transaction.
- **Audit:** each write adds one `audit_log` entry inside the same transaction:
  - actions: `item.create`, `item.update`, `item.cancel`, `item.confirm`, `item.decline`, `item.seen`, `visit.arrived`, `note.create`, `note.convert`, `note.close`, `vehicle.request`, `vehicle.dispatch`, `vehicle.reject`, `vehicle.complete`, `vehicle.withdraw`;
  - `needsConfirm` is recorded on secretary edits; `changes` holds field names and status-like values only, never free text.
- **Notifications:** do **not** queue `notification_jobs`. That is S4-B1.

## 1. `items` handler
Actions and payloads exactly as `store/contract.js`:
- **`list { from, to }`:** active and cancelled items overlapping `[from, to)`. Timed items match on `startAt < to` and `endAt > from`. All-day items match when their `date` falls in the range, read in each item's `tz`; query `date` between the UTC dates of `from - 1 day` and `to + 1 day`, then filter exactly. Then apply visibility. Receptionists and reception admins get visits only.
- **`create { kind, input, needsConfirm }`** and **`createSeries { kind, input, until, needsConfirm }`:**
  - validate with the domain (`validateMeeting` / `validateItem`);
  - permission with `can(...)` exactly as `local.js`;
  - the entry `tz` is the caller's `reminder_prefs.tz`, or `input.tz` when the caller is a secretary or secretaryAdmin entering for a leader (§2);
  - `stop` needs its parent read by id.
  - **Visit with `transport: 'pickup'`:** in the same transaction, add a linked `vehicle_requests` doc:
    - applicant: the caller; `forLeaderId`: none; `passengers`: the visit's `headcount`; `departAt`: the visit's start; `tz`: the visit's; `destination` and `note`: empty bilingual objects `{ 'zh-CN': '', en: '' }`;
    - `reason`: `VISITOR_PICKUP_REASON` from a new `miniprogram/data/labels.js`: `{ 'zh-CN': '接送访客', en: 'Visitor pickup' }`. Chinese is allowed in `data/`, not in `domain/`. Extend `scripts/sync-shared.js` to copy `data/labels.js` into **every** function's `shared/data/`, and use it from `local.js` too;
    - link both ways: `itemId` on the request, `vehicleRequestId` on the visit.
  - Series ids: `items.add` returns the id, but ids must be known before the transaction for the series and for the visit↔request link. Generate them with `crypto.randomUUID()` (injectable `newId` like `randomInt` in admin) and pass `_id` to `add`.
- **`edit { id, patch, expectedRev, needsConfirm, changeNote, scope }`:** `changeItem` from `domain/confirm.js`.
  - `scope: 'following'` applies to occurrences of the same series that start on or after the opened one, with the same rules as `local.js`: `expectedRev` is checked only on the opened occurrence; a `date` change shifts each occurrence by the same number of days.
  - Read the series with a `where({ seriesId })` query **before** the transaction. In the transaction, re-read each occurrence by id. Then update all of them, or none if any check fails.
- **`cancel { id, expectedRev }`:** as `local.js` (`cancelMeeting` for meetings).
- **`confirm` / `decline { reason }` / `seen`:**
  - only the caller's own `leaders[]` entry;
  - for a series, confirm and decline apply to future occurrences (the domain's `applyToSeries`; read the series before the transaction, re-read by id inside it).
- **`arrived { id }`:** `markArrived` from `domain/item.js`.
- **`busy { leaderIds, from, to }`:** `{ slots: [{ startAt, endAt }] }` only; no titles or ids. Same rules as `local.js`.

## 2. `notes` handler
- **`list`:** `noteVisibleTo`, newest first.
- **`create { text }`:** leaders only.
- **`convert { id, itemIds }`** and **`close { id }`:** as the domain; every `itemIds` entry must be an item the caller can see (`item.notVisible`). Transaction plus audit.

## 3. `vehicles` handler
- **`list { from, to }`:** `departAt` in range, then `visibleVehicles`.
- **`request { input }`:** as `local.js` (`forLeaderId` only for self as a leader, or a supported leader as a secretary/secretaryAdmin; drivers cannot request).
- **`dispatch { id, carId, driverId, expectedRev }`:**
  - dispatcher only; the car must be active with enough `seats` for `passengers`; the driver must be an active `driver`.
  - **The car must be free:** no other `assigned` request for that car within ±2 hours of `departAt` (use the domain's existing busy-car rule if there is one, otherwise add one to `domain/vehicle.js`). The same goes for the driver.
  - **Race guard:** reading other requests needs `where`, which a transaction does not allow. So check availability before the transaction, and inside it update a lock doc `locks/car:<carId>:<YYYY-MM-DD in tz>` (and `driver:<driverId>:<date>`) by id, with `rev + 1`. Two concurrent dispatches for the same car and day then conflict, and the transaction retries or fails. The lead documents `locks` in `DATA_MODEL.md`; describe your implementation in the reply.
- **`reject { id, reason, expectedRev }`**, **`complete { id }`**, **`withdraw { id }`:** use the domain `transition` with the rules in §6.

## 6. Tests (new `tests/items-handler.test.js`, `tests/notes-handler.test.js`, `tests/vehicles-handler.test.js`, `tests/docs.test.js`; extend parity)
- **docs:**
  - `toDomain`/`toDoc` round trip with nested `leaders[]` Dates;
  - `_id` never ends up in write data;
  - `fetchAll` pages past 100 and stops at `max`.
- **items:**
  - **visibility matrix:** every seed role against `list`; a secretary sees only supported leaders; a leader never sees another leader's items; a receptionist gets visits only; a driver gets nothing;
  - a `get`, `edit` or `confirm` on an invisible item → `item.notVisible`, with the same answer whether the item exists or not;
  - **create:** each kind, with validation errors passed through;
  - **visit pickup:** creates the linked request in the same transaction, linked both ways;
  - **series:** `createSeries` count and shared `seriesId`; `edit following` moves dates per occurrence and checks `expectedRev` only on the opened one; one failing occurrence rolls back all of them;
  - **rev:** a stale `expectedRev` → `item.alreadyChanged`, and nothing is written;
  - **confirm/decline/seen:** only the caller's own entry changes; the series decline applies to future occurrences;
  - **busy:** returns only `startAt`/`endAt`;
  - **all-day:** an item at the start or end of the range is included in Los Angeles and in Shanghai;
  - **audit:** one entry per write, with `needsConfirm` on secretary edits.
- **notes:** visibility per role; leaders only for create; a convert with an invisible item id → `item.notVisible`; audit.
- **vehicles:**
  - visibility per §4.3: leaders never see non-leader requests; drivers see their assigned ones;
  - `forLeaderId` rules;
  - **dispatch:** non-dispatcher denied; car seats; car busy ±2h; driver busy; inactive car or driver;
  - **lock:** two dispatches for the same car and day where the second has a stale `rev` → `vehicle.alreadyHandled`; the lock doc's `rev` increases;
  - `complete` only by the assigned driver; `withdraw` only by the applicant while pending; `reject` needs a reason;
  - audit.
- **Every handler:** `action.unknown`, `auth.notBound` and `auth.employeeDisabled` gates, and `server.error` hides messages.
