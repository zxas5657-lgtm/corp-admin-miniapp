## 1. The contract: `miniprogram/store/contract.js`
One table, the single source for both implementations and for the B4 handlers. Each entry: `{ method, fn, action }`. `fn` is the cloud function name and `action` the event action. Payloads are listed in a comment beside each entry.

| method | fn.action | payload → result |
| --- | --- | --- |
| `whoami` | `auth.whoami` | `{}` → `{ bound, employee, dispatcher, sysAdmin }` |
| `redeemInvite` | `auth.redeemInvite` | `{ code }` → whoami payload |
| `directory` | `directory.list` | `{}` → `{ rooms, cars, employees }` |
| `listItems` | `items.list` | `{ from, to }` (ISO instants) → `{ items }` |
| `createItem` | `items.create` | `{ kind, input, needsConfirm }` → `{ item }` |
| `createSeries` | `items.createSeries` | `{ kind, input, until, needsConfirm }` → `{ items }` |
| `editItem` | `items.edit` | `{ id, patch, expectedRev, needsConfirm, changeNote, scope }` (`scope`: `'one'` or `'following'`) → `{ item }` or `{ items }` |
| `cancelItem` | `items.cancel` | `{ id, expectedRev }` → `{ item }` |
| `confirmItem` / `declineItem` / `markSeen` | `items.confirm` / `items.decline` / `items.seen` | `{ id, reason? }` → `{ item }` |
| `markArrived` | `items.arrived` | `{ id }` → `{ item }` |
| `busySlots` | `items.busy` | `{ leaderIds, from, to }` → `{ slots }` |
| `listNotes` / `createNote` / `convertNote` / `closeNote` | `notes.list` / `notes.create` / `notes.convert` / `notes.close` | `{}` / `{ text }` / `{ id, itemIds }` / `{ id }` → `{ notes }` or `{ note }` |

| `getPrefs` / `updatePrefs` | `prefs.get` / `prefs.update` | `{}` / `{ patch }` → `{ prefs }` |

Every method returns a Promise of `{ ok: true, ...result }` or `{ ok: false, code }`. Export `METHODS`, the list of method names. Add a test that every method has a unique `fn.action` and that `fn` names an existing `cloudfunctions/` folder.

## 2. Wire format: `miniprogram/store/wire.js`
- `fromServer(value)` deep-converts server documents to the client shape:
  - `_id` → `id` (keep nested objects intact);
  - Dates (a `Date`, or `{ $date: number|string }` as `wx.cloud.callFunction` may return) → ISO strings ending in `Z`;
  - all other values unchanged.
- `toServer(value)` does the reverse for payloads: drop any `id`/`_id`/`createdAt`/`updatedAt`/`rev` the client must not set. Instants stay ISO strings; the server converts them.
- Tests for nested arrays (`leaders[]`), null dates and idempotence.

## 3. Remote API: `miniprogram/store/remote.js`
- `createRemoteApi({ call, onAuthLost })`. `call(fn, data)` is injected; in the app it is `(name, data) => wx.cloud.callFunction({ name, data }).then((r) => r.result)`, exported as `wxCall` and written so requiring the file in Node does not touch `wx`.
- Each method sends `{ action, ...toServer(payload) }`, then applies `fromServer` to the result.
- Errors:
  - A thrown or rejected call, or a result that is not an object with a boolean `ok`, becomes `{ ok: false, code: 'network.failed' }`.
  - Server codes pass through unchanged.
  - If the code is not a key under `error.` in the en locale, it becomes `server.error`. Read the key list from `i18n/en.js`; this is a static check, not a translation.
- `auth.notBound` and `auth.employeeDisabled` also call `onAuthLost(code)` once per occurrence.
- No retries inside the API; pages own retry (S3-F1).

## 4. Local API: `miniprogram/store/local.js`
`createLocalApi({ store, actor, clock, ctx, newId })`. It implements every contract method on top of the existing synchronous store and domain rules, so the demo and tests behave like the server will:
- **Reads** filter with `domain/visibility.js` for `actor` and `ctx.supports`. List ranges use the instants: an item is in range when it overlaps `[from, to)`, and an all-day item when its day touches the range in `item.tz`.
- **Writes** call the domain (`createItem`, `createSeries`, `changeItem`, `confirmItem`, …) with `actor` and `clock.now()`. They check `expectedRev` (`item.alreadyChanged`), store through `store.updateItem` and friends, and return the saved record.
- `newId(prefix)` is injected; the default is a counter, never `Math.random`.
- **Auth:**
  - `whoami` returns the actor's directory entry from `data/reference.js`, `bound: true`.
  - `redeemInvite` returns `{ ok: false, code: 'action.unknown' }`.
  - `directory` comes from `data/reference.js`.
- **Prefs** live under a new storage key through the store's adapter, with the same defaults and validation as `cloudfunctions/prefs/handler.js`. Move that validation into `miniprogram/domain/prefs.js` and have the cloud handler require it from `shared/domain/prefs.js`. The lead runs `npm run sync`.
- **Operations without domain logic yet** (`markArrived`, `vehicles.reject/complete/withdraw`): implement them with the rules in `DATA_MODEL.md` §6 and put the pure transition in the domain file (`vehicle.js` or `item.js`), with tests. Keep it small.

## 5. `miniprogram/store/api.js`: choosing the implementation
- `createApi({ mode, ... })` with `mode` `'local'` or `'remote'`.
- `getApi()` is a singleton like `getStore()`. It reads `mode` from `miniprogram/config.js`, adding `DATA_MODE: 'local'` there. The app keeps working offline exactly as now until the owner flips it after the env exists.
- Add `CLOUD_ENV: ''` to `config.js` with a comment: the dev env id goes here later (not a secret, per `DATA_MODEL.md` §3). Do **not** call `wx.cloud.init` anywhere yet; S3-F1 wires it.

## 6. Tests
- A **contract test** runs the same scenarios against the local API and against the remote API, where the remote's `call` is routed to an in-process fake. The fake maps `fn.action` to a small handler table in the test: only the actions that exist today (`auth.whoami`, `directory.list`, `prefs.*`), backed by the real `cloudfunctions/*/handler.js` and the fake DB. Every other action is skipped for the remote side, with `test.todo` naming B4.
- **Remote errors:** a rejected call, `undefined`, `{}`, an unknown code (→ `server.error`), each `onAuthLost` trigger, and Date/`$date`/`_id` conversion.
- **Local API:**
  - visibility per role (secretary sees only supported leaders; receptionist sees visits and busy slots only);
  - a series of create, edit (`following` scope), confirm, decline and cancel;
  - `expectedRev` mismatch → `item.alreadyChanged`;
  - notes convert/close;
  - vehicle request → dispatch → complete, and withdraw while pending;
  - prefs validation;
  - every write calls the store and notifies subscribers.
